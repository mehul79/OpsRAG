# OpsRAG benchmark

How retrieval and answer quality were measured, what the numbers are, and what they do not show.

**Run date:** 2026-11-02 · **Questions:** 37 (35 answerable, 2 unanswerable) · **Index:** 48,572 chunks · **Judge:** `openai/gpt-6-luna`

## Summary

| Metric | Score | What it tells you |
| --- | --- | --- |
| recall@20 | **1.000** | The right doc reached the candidate set for every answerable question |
| recall@5 | **0.971** | The right doc was in the final top 5 for 34 of 35 questions |
| MRR@5 | 0.736 | The first right doc is usually rank 1 or 2 |
| precision@5 | 0.514 | About half of the top 5 come from the expected doc (see the labelling caveat below) |
| NDCG@5 | 0.543 | Ordering quality of the reranked top 5 (binary relevance) |
| weak-flag accuracy | **1.000** | Unanswerable questions were flagged weak, answerable ones were not |
| context relevancy | 0.857 | Share of top-5 chunks an LLM judged useful for the question |
| answer relevancy | 0.971 | The answer addresses the question (33 of 35 fully, 2 partly) |
| faithfulness | 0.967 | Share of answer claims supported by the retrieved chunks (27 of 35 answers fully) |

These are small-sample results from one run on one dataset. Read them as a regression baseline and a way to compare changes, not as a general quality claim. See [Limitations](#limitations).

## System under test

| Part | Setting |
| --- | --- |
| Corpus | Kubernetes, Docker, Terraform (core + AWS provider), AWS (EC2, ECS, EKS, IAM, CloudFront, RDS, ELB) |
| Index | Qdrant, one collection, 48,572 chunks (after merging 26 exact duplicates), dense + BM25 vectors |
| Chunking | Split at h1 to h3 headings, code fences kept whole, max 1,500 characters, heading path stored with each chunk |
| Dense embeddings | `BAAI/bge-small-en-v1.5` (384-d), documents embedded on a Colab GPU, queries on CPU via ONNX |
| Sparse | `Qdrant/bm25` with Qdrant's IDF modifier |
| Fusion | Reciprocal rank fusion of dense and BM25 candidates, top 20 after removing exact-text duplicates |
| Reranker | `Xenova/ms-marco-MiniLM-L-6-v2` cross-encoder (local, CPU), top 20 to 5 |
| Query rewrite | **Off** for the numbers above (`--no-transform`) |
| Generator | `deepseek/deepseek-v4.1-flash` through OpenRouter, reasoning disabled |
| Judge | `openai/gpt-6-luna` through OpenRouter, reasoning disabled |

Chunk counts per source: k8s 6,401 · aws-iam 6,359 · aws-ec2 6,014 · aws-eks 5,942 · docker 5,812 · aws-ecs 4,384 · terraform-aws 3,625 · aws-rds 3,236 · terraform-core 2,852 · aws-cloudfront 2,603 · aws-elb 1,344.

## Dataset

`evals/dataset.jsonl`, generated by `evals/make_dataset.py`.

- **37 questions:** 35 answerable and 2 unanswerable ("How do I make pizza dough?", "What is the weather in Mumbai today?").
- **Kinds (answerable):** howto 13, concept 12, exact-identifier 5 (for example `aws_s3_bucket_versioning`), compare 3, vague 2.
- **Spread:** 10 Kubernetes, 6 Docker, 5 Terraform core, 5 Terraform AWS, 7 AWS service docs, plus 2 vague and 2 unanswerable.
- **Authorship:** drafted with an AI assistant, then each expected path was checked against the corpus.

### Labels

Each answerable question has one regular expression over the chunk's file path (for example `terraform/aws/r/iam_role_policy_attachment`). A retrieved chunk counts as relevant if its path matches. `make_dataset.py` refuses to write the file unless every pattern matches at least one real file in `data/`, so a typo in a label cannot silently turn into a guaranteed miss.

Two questions were revised after a first run showed that the label, not the retriever, was wrong:
- "How do I create an EKS cluster with Terraform?" now accepts either the Terraform resource page or the AWS EKS Terraform guide.
- A resource-limits question was made explicit about Docker because the unqualified version legitimately matched Kubernetes pages.

The Docker volumes miss below was kept as a real miss.

## Metrics

Let a question have a relevance pattern, `cands` be the 20 fused candidates, and `top` the 5 chunks after reranking.

| Metric | Definition |
| --- | --- |
| recall@20 | 1 if any candidate matches the pattern, averaged over answerable questions |
| recall@5 | 1 if any of `top` matches, averaged |
| MRR@5 | 1 / rank of the first matching chunk in `top` (0 if none), averaged |
| precision@5 | matching chunks in `top` / 5, averaged |
| NDCG@5 | Binary-relevance DCG of `top`, divided by the ideal DCG. The ideal places every relevant candidate (up to 5) first |
| weak-flag accuracy | Over all 37 questions: unanswerable ones flagged weak and answerable ones not flagged |

### LLM-judged metrics (`--judge`)

For each answerable question the pipeline generates an answer from the chunks that survive the weak-retrieval check, then the judge model grades it with three prompts, each returning JSON.

| Metric | Prompt asks | Score |
| --- | --- | --- |
| context relevancy | For each numbered chunk, does it contain information that helps answer the question? | relevant chunks / chunks |
| faithfulness | Split the answer into factual claims (ignoring citation markers and statements that the docs do not cover something), and mark each as supported by the context or not | supported claims / claims |
| answer relevancy | Does the answer directly address the question? | 1, 0.5 or 0 |

All three are averaged over the 35 answerable questions. There were 0 judge errors (unparseable replies) in the run.

**Judge sanity check.** Before the full run, a deliberately fabricated answer ("run `kubectl probe enable`, requires a paid license, probes run every 3 hours") was graded against real context. It scored faithfulness 0.0 and answer relevancy 0.0, while real answers scored 0.83 to 1.0. This shows the judge can tell unsupported text from supported text. It does not show that its scores are calibrated.

### Weak-retrieval threshold

The top-1 reranker score separates the two groups cleanly: the lowest top-1 score among answerable questions was **1.89**, and the highest among unanswerable ones was **-9.64**. The threshold of 0.0 sits in a wide gap, so weak-flag accuracy of 1.000 is not a close call. With only two unanswerable questions this says little about borderline cases.

## What the numbers show

- **Retrieval is strong where it has been tested.** The right document is always among the 20 candidates, and it is in the top 5 in 97% of cases. Exact identifiers (where BM25 matters) all succeeded.
- **The one miss:** "How do I persist data with Docker volumes?" The canonical `volumes.md` ranked 11th before reranking, and the reranker then preferred two tutorial pages over it. The answer can still be reasonable, since those pages also cover volumes, but the reference page was not in the top 5.
- **The weakest group is vague, symptom-style questions.** "my pod keeps restarting after deploy" scored context relevancy 0.4 and answer relevancy 0.5 even though its labelled doc was found at rank 1. The retrieved chunks were relevant to restarts in general, but not specific to the question. There are only two such questions, so this is a lead for more tests, not a conclusion.
- **Precision and NDCG read low by construction.** Each question has one path pattern, so a correct chunk from a different page counts as wrong. NDCG is also pulled down when many relevant candidates exist and only some reach the top 5. These two metrics are most useful for comparing changes against each other.
- **The LLM query rewrite did not help on this set.** An earlier run with the rewrite enabled scored recall@5 0.943 (one question fewer) against 0.971 without it, and the rewrite adds about 2 s. Precision, NDCG and the judged metrics were not measured with the rewrite on.
- **Faithfulness is high but not perfect.** 27 of 35 answers had every claim supported, and the lowest answer scored 0.75. This is a judged number, and a judge can miss subtle errors.

## Limitations

- **Small sample.** 35 answerable questions. One question moves recall@5 by about 3 points, and the vague and compare groups have 2 and 3 questions.
- **Single-pattern labels.** Alternative correct sources are missed, which depresses precision and NDCG and can hide good retrievals.
- **Questions were written to be answerable from this corpus.** They are cleaner and more explicit than real user questions.
- **LLM judge.** One judge model, one run, no repeated runs, no comparison against human grading. A different judge may score differently. The judge sees the same chunks the generator saw, so it can only check support, not whether the chunks themselves were the best available.
- **Answerable questions only for answer metrics.** Behaviour on unanswerable questions was checked with the weak flag, not graded for answer quality.
- **No latency or load benchmark.** The few timings recorded informally (about 10 s per uncached answer on a 4-core laptop, most of it LLM calls and CPU reranking) are not part of this benchmark.
- **Index and models are fixed.** The results are for this chunking, embedding model and reranker. They do not generalize to other settings.

## Reproduce

```bash
# deterministic metrics, no LLM calls (this is what the regression check runs)
uv run python evals/run.py --no-transform

# adds generation and the three LLM-judged metrics (about 8 minutes, a few cents)
uv run python evals/run.py --no-transform --judge

# include the LLM query rewrite
uv run python evals/run.py
```

Results are written to `evals/results/latest.json`, including every question's retrieved paths, ranks, scores, generated answer and judge scores, so each number can be traced to its rows. Set `JUDGE_MODEL` in `.env` (default `openai/gpt-6-luna`).

## Regression check

`python evals/run.py --no-transform --check` compares recall@20, recall@5, precision@5, NDCG@5 and weak-flag accuracy with `evals/baseline.json` and exits non-zero if any drops by more than 0.03. LLM-judged metrics are excluded from the check because they cost money and vary between runs. `tests/test_gate.py` tests the gate and NDCG logic.

The baseline should be refreshed only for an intended change: copy the `metrics` from `evals/results/latest.json` into `evals/baseline.json`.
